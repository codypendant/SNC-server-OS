============================================================
1. WHAT PR #80 CLOSED
============================================================

PR #80 closed the final two S3 blockers.

A. Raw runtime lifecycle escape hatch is closed

`Engine::runtime()` is gone.

External shard work now goes through `Engine::DataPlane`, which is a lifecycle-counted lease.

Required invariant now holds:

No external code may submit work to an Engine runtime without holding a lifetime token that `stop()` waits on.

Accepted behavior:
- lease granted only in RUNNING;
- STOPPING refuses new leases;
- STOPPED refuses new leases;
- stop waits for outstanding leases;
- moved leases retain exact accounting;
- `run_on_all()` from a shard thread aborts instead of self-deadlocking;
- read-only runtime facts go through `RuntimeView`, not a raw runtime reference.

This closes the same abandoned-waiter defect class that S3.2 fixed for Engine methods.

B. Promotion vs checkpoint durable-state race is closed

`promote()` and `checkpoint()` now hold one durable-control lock:

`control_mu_`

They therefore linearize as one of exactly two orders:

Order A:
checkpoint completes under standby role -> promotion

or

Order B:
promotion completes -> checkpoint runs under primary role

Hybrid durable state is no longer allowed.

This protects shared mutations of:
- `sb_.term`
- `sb_.generation`
- `sb_.active_ckpt`
- lease fields
- `next_lease`
- runtime role
- superblock persistence

Runtime role was correctly separated from immutable configuration.

`cfg_.standby` is no longer mutated as runtime state.

`term()` and `lease_block()` now read a published superblock view rather than racing raw `sb_`.

============================================================
3. S3 FINAL ARCHITECTURE
============================================================

The S3 checkpoint path is now:

1. S2 time-paces the checkpoint WALK.
2. Checkpoint records are produced into bounded chunks.
3. S3 uses `RWF_DSYNC` per checkpoint chunk.
4. At most W chunk writes are in flight per shard.
5. A full window structurally stops further checkpoint production.
6. Each write owns its own buffer until its own completion.
7. Completed buffers are freed immediately.
8. Retained checkpoint memory is bounded by the write window rather than checkpoint size.
9. Positive short writes are fatal.
10. Synchronous fallback is observable and invalidates performance evidence.
11. Final `fdatasync` remains the correctness barrier.
12. Engine lifecycle prevents runtime teardown underneath active work.
13. Durable-control operations that touch the same persistent metadata are serialized.

CC-1 through CC-5 remain unchanged.

Do not broaden the slice.

============================================================
5. S4 OBJECTIVE
============================================================

Current concern:

Even with S3 bounded `RWF_DSYNC` writeback, multiple shards may still reach their final `fdatasync` at roughly the same time.

S4 must prevent all shards from issuing their final sync concurrently.

Desired structure:
- shard finishes WALK;
- all chunk writes complete;
- local WAL has reached `max_lsn`;
- shard requests a sync token;
- only K shards may hold a sync token simultaneously;
- token holder issues final `fdatasync`;
- completion releases token;
- another waiting shard may proceed.

The checkpoint still commits only after every shard has completed its part.

============================================================
6. S4 DESIGN RULES
============================================================

K is a hypothesis.

Do not freeze K=1.

Support/configure a bounded concurrency value and test at least:
- K=1
- K=2
- K=4
- K=8 / effectively unlimited

The selection criterion is NOT raw checkpoint throughput.

The question is:

What is the smallest sync concurrency that protects WAL service behavior while still allowing acceptable checkpoint completion time?

S3 should already have made final sync relatively small. S4 exists to bound concurrency, not redesign checkpoint I/O.

============================================================
8. S4 CORRECTNESS MODEL
============================================================

Staggering sync does not change checkpoint atomicity.

Parts are allowed to become durable at different times.

Before the superblock commit:
- a crash recovers from the previous checkpoint plus retained WAL.

After the superblock commit:
- the new checkpoint is authoritative.

This remains CC-5.

S4 only changes when each shard may perform final part sync, not what is written or when the checkpoint becomes visible.

============================================================
9. TOKEN REQUIREMENTS
============================================================

S4-I1 — hard concurrency bound

At most K shard final-sync operations may be active at one time.

S4-I2 — no token leak

Every token acquisition must have one matching release.

Release must occur on:
- successful sync completion;
- fatal/error path as applicable before process termination;
- any supported cancellation path, if one exists.

S4-I3 — no starvation

A shard waiting for a token must eventually receive one if active syncs continue completing.

S4-I4 — no shard-thread blocking

Waiting for a token must not block the shard thread with a mutex/condition wait.

The shard must continue polling:
- WAL completions;
- foreground work;
- follow-ups;
- runtime I/O;
- control work.

Token wait must be state-based/poll-based or otherwise nonblocking.

S4-I5 — checkpoint completion

All shards eventually sync and report completion.

The node checkpoint cannot commit before every shard reports.

S4-I6 — rollback

Unlimited mode must restore current S3 sync behavior for differential testing.

============================================================
10. FAIRNESS
============================================================

Do not create a token implementation where one shard can repeatedly reacquire while others starve.

Prefer an explicit waiter/order model or a token allocator with deterministic fairness.

We do not need sophisticated scheduling, but we do need a credible progress argument.

Document it.

============================================================
12. REQUIRED S4 TESTS
============================================================

S4-T1 — hard K bound

Make all shards ready to final sync simultaneously.

Hold completions.

Prove:
`active_syncs <= K`

at every observation.

Test K=1,2,4 and unlimited.

S4-T2 — exact token release

Allow one sync completion.

Prove exactly one waiting shard may advance into sync.

Repeat until all finish.

S4-T3 — fairness / progress

Hold and release syncs in controlled order.

Prove every waiting shard eventually acquires a token.

S4-T4 — foreground progress while waiting

Keep shards waiting for tokens.

Prove normal foreground operations/WAL polling continue.

Token waiting must not block shard loops.

S4-T5 — crash during staggered sync

Crash with:
- zero shards synced;
- some shards synced;
- all shards synced but before manifest;
- manifest/superblock boundary where existing crash tests apply.

Recovery must be exact.

S4-T6 — sync failure

Inject a final-sync failure while a token is held.

Verify checkpoint does not commit and previous checkpoint remains authoritative.

S4-T7 — unlimited rollback

Unlimited mode allows the same final-sync concurrency as pre-S4.

Existing correctness tests must pass.

S4-T8 — token accounting

acquisitions/releases/current/peak/waiters reconcile exactly.

S4-T9 — repeated checkpoints

Run many checkpoints and verify no token count drift or starvation accumulates across checkpoints.

S4-T10 — negative mutation

Bypass token acquisition or allow K+1 syncs.

The test must fail.

Also add a mutation for token leak if practical.
