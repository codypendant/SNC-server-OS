BLOCKER F1 — CLOSED LOOP

The current depth sweep is closed-loop and subject to coordinated omission. It cannot set the p99 objective. The stopped physical run is invalid for criteria/campaign evidence.

AUTHORIZE NARROW OPEN-LOOP FIX

Add net_bench --rate R:
- total offered ops/s across threads;
- deterministic intended issue schedule;
- latency measured from intended issue time through completion;
- depth bounds outstanding work/memory, not offered rate;
- if slots are full, owed work waits and its delay counts;
- never silently drop scheduled work;
- report offered/completed/achieved rate, owed/late/backlog, maximum issue lateness, errors and latency percentiles;
- deterministic thread division/remainder;
- tests must prove scheduling arithmetic and that forced stalls appear in latency/backlog.

Prefer deterministic periodic arrivals with per-thread phase offsets. Poisson/random arrivals are a later named workload dimension.

RATE SWEEP

Approve the structure:
calibration only to size grid -> open-loop grid -> 3 reps/point -> fixed-seed shuffled order -> sustained test -> stable peak -> objective at fixed fraction.

Do not freeze the draft's 5% x 1..22 grid or f=0.70 merely because they are written down.

Before real pilot, PILOT_PLAN must fix:
- calibration duration/depth;
- offered-rate grid;
- warm-up;
- measurement duration;
- reps;
- sustained criterion;
- backlog definition/drain window;
- overload/error handling;
- stable-peak rule;
- objective fraction f;
- informational knee rule;
- tie breaking;
- early-stop rule.

SUSTAINED

Every rep:
- zero protocol/application errors;
- completed throughput >=99% offered;
- end backlog <=1% scheduled;
- no dropped-work overload counter.

If owed work cannot drain within bounded drain time, mark unsustained and record remaining backlog.

Stable peak = largest rate whose point AND all lower points are sustained.

Keep knee informational. Proposed descriptive knee: smallest sustained rate whose median p99 >2x median p99 at first grid point.

f=0.70 remains PROPOSED and must be approved before data exists.

CPU/NUMA ALLOCATION

Current draft hard-codes server node0 / client node1. That is PILOT-X, not the desired baseline.

CP-1A must support explicit allocation.

PILOT-L:
server and clients on disjoint physical cores on node0, memory local node0, housekeeping reserved, server SMT siblings idle.

PILOT-X:
server node0, clients node1, explicitly cross-socket/UPI.

Use the approved baseline allocation for criteria-setting, not forced cross-socket traffic.

Before shard sweep, budget physical cores among server/client/housekeeping. For high server-core counts, a second client host may eventually be necessary. It is acceptable to cap the local-socket primary sweep where client capacity remains sufficient and classify larger runs separately.
