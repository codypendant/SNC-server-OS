PR #69 REVIEW — S0 OBSERVABILITY

DECISION

S0 is APPROVED IN ARCHITECTURE AND SCOPE, but PR #69 has one blocking concurrency-correctness issue in the published-gauge seqlock plus one evidence wording issue.

Do NOT start S1 yet.

Fix S0.1 narrowly, rerun the required suites, and return once. No R640 load is needed.

1. S0 SCOPE — APPROVED

The implementation stayed inside the authorized S0 boundary:
- observability only;
- no admission behavior change;
- no waiter/WAL budget enforcement;
- no overload-gate move;
- no checkpoint pacing;
- no checkpoint I/O change;
- no fdatasync ordering change;
- no kEmitBacklog change;
- no protocol-status change;
- no recovery/reclamation change;
- no R640 load.

The permanent-gauge architecture is the correct replacement for the invasive diagnostic polling.

2. PUBLISHED GAUGE ARCHITECTURE — APPROVED IN PRINCIPLE

Per-shard single-writer published blocks are the right design.

Good properties:
- shard owns updates;
- no synchronous task submission to measured shards;
- no locks/allocations/syscalls on hot counter updates;
- GAUGES/HEALTH read published state directly;
- publication rate is bounded;
- node checkpoint gauges are separately documented as individually atomic, not transactionally coherent.

Keep this architecture.

3. BLOCKER: SEQLOCK READER MEMORY ORDERING

include/snc/gauges.h currently does approximately:

writer:
  seq odd store(relaxed)
  release fence
  relaxed field stores
  seq even store(release)

reader:
  s1 = seq load(acquire)
  relaxed field loads
  acquire fence
  s2 = seq load(relaxed)

I do NOT approve this memory-ordering pattern as the final seqlock.

The second sequence load must participate in an acquire ordering relationship with the writer's final release publication. An acquire fence placed BEFORE a relaxed second load is not a substitute for an acquire load of that sequence value.

TSan passing does not prove snapshot coherence; this is a logical memory-model issue, not necessarily a data race.

Use a conventional, auditable pattern.

Preferred minimum:

writer:
  seq.store(odd, release or appropriate ordered RMW/store)
  write fields
  seq.store(even, release)

reader:
  s1 = seq.load(acquire)
  if odd -> retry
  read fields
  s2 = seq.load(acquire)
  accept only if s1 == s2 and even

An equally correct acquire/release seqlock pattern is acceptable, but document the C++ memory-order reasoning.

Do NOT use seq_cst everywhere merely to make the question disappear unless measurement shows the cost is irrelevant; acquire/release is sufficient if implemented correctly.

4. ADD A MEMORY-ORDER CONTRACT COMMENT/TEST

Keep the existing T7 concurrency stress test.

Add a source/design comment explaining the publication contract:
- odd sequence means publication in progress;
- reader may accept fields only when two ACQUIRE sequence reads return the same even generation;
- final writer RELEASE publishes all preceding field stores.

The code should be simple enough for review without relying on a subtle fence idiom.
