PR #72 REVIEW — S1 RESOURCE-SPECIFIC ADMISSION

DECISION

PR #72 is NOT yet approved as the completed S1 slice.

The architecture and most of the implementation are directionally correct, and the clean Release/ASan/TSan evidence is good. However, the PR itself documents two issues that violate the S1 contract strongly enough that I do not want to carry them into S2:

1. the WAL reservation is not actually a worst-case reservation for all legal object sizes;
2. the remote-read / pending-waiter path remains unbounded.

There is also one newly characterized validation-harness measurement defect that should be fixed on site rather than carried forward.

Do NOT start S2.

Make an S1.1 correction and return.

============================================================
1. WHAT IS APPROVED
============================================================

The following S1 design choices are approved:

- resource-specific admission;
- owner-local durable reads no longer refused merely because mutation follow-ups exceed kEmitBacklog;
- mutation/create/delete follow-up gating;
- waiter-budget admission;
- WAL-buffer-budget admission;
- reserve/check after validation and before first irreversible mutation;
- E_OVERLOADED remains the wire status;
- refused_* gauges identify the limiting resource;
- kEmitBacklog stays 1,024;
- internal/already-acknowledged work remains non-refusable;
- legacy switch for differential testing;
- loop order unchanged;
- checkpoint/recovery/CC-1..CC-5 unchanged.

The general reserve-before-mutate placement in run_exec/run_create/run_delete is correct.

============================================================
2. BLOCKER A — RESERVATION IS NOT ACTUALLY WORST-CASE
============================================================

docs/S1_ADMISSION.md explicitly acknowledges this:

- prepare_ctx sets reserved_len_ to allocator-rounded object capacity;
- OpCtx::resize can grow the object beyond type.max_size up to capacity;
- S1 reserves record_size(type.max_size);
- therefore an admitted op can append more WAL bytes than its reservation;
- create has no local-peer slack to hide it;
- a mutation with a near-max local peer can also exceed the reservation.

This violates the requirement from PR #71 that worst-case WAL sizing cover every synchronous record generated by the call.

It also means check_reserved can abort on a legal state in debug builds while release builds can silently exceed the budget.

Do not defer this to “before S6.” Fix it now.

============================================================
3. REQUIRED RESERVATION FIX
============================================================

Choose and prove one approach:

A. RESERVE ACTUAL LEGAL CAPACITY

For existing objects, reserve record_size(current object capacity) if capacity is truly the maximum legal payload the op can reach before another allocation/re-entry.

For CREATE, derive the maximum legal post-create record from the actual allocation/resize contract before mutation.

OR:

B. MAKE type.max_size A TRUE HARD CAP

Change OpCtx::resize/reserve semantics so no op can produce an object larger than type.max_size.

This is a broader semantic change and needs extra review.

Preferred for S1.1: A, if it can be implemented without changing application semantics.

Whichever is chosen:

- no valid op may append more than its reservation;
- check_reserved becomes a proof check, not a detector of a known legal mismatch;
- add deterministic near-size-class tests;
- include CREATE;
- include near-max local peer;
- include sequenced/session record.

============================================================
4. BLOCKER B — REMOTE READ WAITERS / PENDING ARE STILL UNBOUNDED
============================================================

The S1 document correctly admits:

- a READ served for another shard may add a REMOTE waiter at the owner;
- the owner never refuses it;
- origin pending_ is unbounded;
- the origin follow-up gate does not bound pending reads.

That means S1 still has an unbounded admission path for the durability-waiter resource it claims to bound.

This conflicts with the S1 principle that reads using waiters, forwarding, pending slots, rings, gather resources, or output buffering remain bounded by those resources.

Do not call S1 complete while this path is unbounded.

============================================================
5. REMOTE READ BOUND — REQUIRED DESIGN
============================================================

Add a bounded remote-read path before S1 is complete.

Preferred shape:

- add an explicit per-origin pending budget and/or owner REMOTE-waiter budget;
- refuse before creating unbounded pending/waiter state;
- preserve E_OVERLOADED wire status;
- count the exact cause in gauges/stats;
- preserve already-issued/internal progress;
- avoid a deadlock where the response required to free a pending slot cannot be delivered.

The exact location can be origin-side, owner-side, or both, but the proof must show a global bound.

Do not use the unrelated follow-up backlog as a proxy bound.

If a protocol-field change is genuinely required, stop after the narrow design and return for review before coding it. If it can be done additively with existing E_OVERLOADED semantics, implement it in S1.1.

============================================================
6. INTERNAL WORK OVERSHOOT — DOCUMENT THE REAL MEMORY BOUND
============================================================

The current budget derivation presents roughly 32 MiB active + 32 MiB flushing while also acknowledging non-refusable follow-ups may exceed the client budget.

Do not characterize the client admission budget as a hard memory bound.

With multiple senders, backlog ~1,025 each, and large legal records, internal follow-up WAL growth can be far larger than the typical ~300-byte-record estimate.

For S1.1:

- derive a conservative upper bound for non-refusable internal WAL growth from existing backlog limits and maximum legal record size;
- distinguish CLIENT ADMISSION BUDGET from ABSOLUTE POSSIBLE WAL MEMORY;
- if the absolute bound is too large or not finite, identify the next architectural bound explicitly.

Do not hide this with average-record math.

============================================================
7. 32 MiB / 30 MiB DEFAULTS — PROVISIONALLY ACCEPTABLE, NOT FROZEN
============================================================

The R2-based derivation is reasonable as a provisional client-admission choice:

- 32 MiB waiter budget;
- 30 MiB WAL admission budget.

Accept them provisionally for continued software work.

They are NOT validated production defaults.

Revisit them with physical evidence after S2-S4 and before S6.

Keep the assumed 1 GB/s drain calculation explicitly labeled hypothetical.

============================================================
8. TEST A6 — TIGHTEN IT
============================================================

The document itself notes A6 should assert all 200 transfers were actually sent/applied.

Fix that now.

A non-refusable-internal-work test must prove:

- expected number of follow-ups emitted;
- expected number applied;
- client admission gate actually closed;
- internal work crossed client WAL budget;
- all work drained;
- final state/money conservation exact.

Do not allow partial-send behavior to make the test pass.

============================================================
9. NEW HARNESS DEFECT — q4_normal
============================================================

The failed ASan run exposed a real measurement defect in test_baseline_ha q4_normal:

- RESOURCES is aggregated by sequential per-shard stats calls rather than a coherent snapshot;
- the final “drained” judgment uses one instantaneous end sample while load is still active;
- the sum can report > client window because work advances between shard samples.

This is not evidence of an S1 engine defect.

But fix known measurement ambiguity on site.

Required narrow correction:

A. Use S0 published gauges for waiter/undurable state where possible because they do not synchronously submit shard tasks.

B. Define a coherent drain criterion over a bounded observation interval, for example N consecutive samples or a preregistered median/max rule.

C. Preserve the original q4 intent: prove bounded progress and no ever-growing client-durability backlog after grant.

D. Add a deterministic/synthetic check showing the old sequential-sum method can exceed the client window even when each shard is individually valid.

Do not simply change to “median last 5 seconds” without defining what drained means.

============================================================
10. CREATE / MOVED PRECEDENCE — ACCEPT FOR NOW
============================================================

E_OVERLOADED may precede E_MOVED for create/delete under backlog.

Accept for now because:
- both are retryable;
- no state changes;
- retry reveals E_MOVED after backlog drains.

Keep documented.

============================================================
11. MINTED CREATE ID ON REFUSAL — ACCEPT FOR NOW
============================================================

A refused create may consume an ObjectID that never becomes an object.

Given non-reuse, this is safe.

Clients must ignore IDs on non-OK responses.

No S1.1 change required.

============================================================
12. LEGACY SWITCH — KEEP
============================================================

Keep --admission legacy for differential testing and reproduction of pre-S1 behavior.

============================================================

Add/strengthen at least:

A11 — create boundary

Release durability; pending/waiters drain; admission reopens; no lost/double responses.
