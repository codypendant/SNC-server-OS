11. REDIS INDEX SEMANTICS — DO NOT HIDE THE MISMATCH
============================================================

Workload A includes secondary-index queries.

Plain Redis does not provide the same secondary-index primitive as SNC/PostgreSQL.

Do not quietly implement a client-maintained index and call the semantics equal.

Before comparative testing, choose and document one of:

A. Redis + an explicitly named indexing component/data structure maintained by the service, with its write/update cost included.

B. Mark Redis's index-query cell as a semantic mismatch and exclude that specific metric from direct matched comparison.

C. Use an appropriate Redis search/index module if the chosen competitor definition explicitly includes it, pinning version/configuration.

The semantics table must make the choice obvious.

============================================================
12. RESOURCE METRICS — DEFINE BEFORE IMPLEMENTATION
============================================================

G3 is directionally correct, but avoid ambiguous counters.

Before CP-1A/B implementation, define:

CPU per op:
process CPU time consumed by server-side processes included in the system boundary / successful measured operations.

Memory per object:
define whether peak RSS, steady-state RSS, or incremental RSS over empty process is primary. Prefer incremental steady-state plus peak reported separately.

Storage bytes/op:
do not assume /proc/<pid>/io write_bytes equals physical media bytes. It is useful host-visible I/O accounting, but label it correctly. If device-level bytes are used, isolate the device/system sufficiently to attribute them.

Network bytes/op:
define interface/device counter boundaries and subtract idle/background traffic where practical. For localhost pilot, network bytes are not physical-NIC evidence.

All systems must use the same accounting boundary as far as practical.

Document unavoidable mismatches.
