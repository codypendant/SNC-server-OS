**Classification (item 5)**

## Review 2: benchmark equivalence (items 2, 3; section 4): 14 findings, 2 blocking

Adversarial review of section 4 in docs/DIRECTION_COMPARISON_PLAN.md (revision 2). I edited nothing. Facts I checked in the repo: the mix arithmetic is right (`--transfer 20 --reads 50` gives 40/40/20, net_bench.cpp 755-758). The 1-in-8 same-shard figure is right at 8 shards. The R640 data SSD reports `WCE 1, fua=1` (R640_TOPOLOGY.md line 40). WAL segments are created with `fallocate` (storage.cpp 554/786). Writes use `RWF_DSYNC` (runtime.cpp 213).

**1. BLOCKING: the replay rule is wrong in both directions.**
Text: "replayed only up to the last flush or FUA before that mark".
- A FUA makes only its own write durable. It does not cover earlier writes still in the cache. So treating a FUA as a barrier lets a system pass while not durable: Garnet Native's unflushed O_DIRECT writes would count as durable if any unrelated FUA write follows them, such as an ext4 journal commit block.
- Replaying only to the last flush has the opposite fault. SNC's O_DIRECT+RWF_DSYNC overwrite of an already-written segment issues FUA with no flush, so SNC would fail while durable.

Smallest fix: run the test on an underlying device set to `queue/write_cache = write back` and `queue/fua = 0`. The block layer then turns every FUA into write plus flush, and the replay goes to the last FLUSH only. Record both sysfs values in the manifest.

**2. BLOCKING: the test proves nothing unless the device sends flushes, and it has no controls.**
- Many cloud virtual disks report write-through. The kernel then strips PREFLUSH/FUA before they reach dm-log-writes, so the log holds no flush entries. Every system then fails, or, if the log is read naively, every system passes.
- Fix: put dm-log-writes over a loop device or a device set to write-back by sysfs.
- Add two controls on every test host before any system runs. A positive one: `fio --direct=1 --fsync=1`, which must pass. A negative one: `fio --direct=1` with no sync, which must fail.
- Run mkfs through the logged device, with a mark "mkfs", as xfstests generic/482 does. Use dm-thin snapshots per mark, so each replay is not a full replay from the start.

**3. MAJOR: the R640 confirmation cannot see FUA durability.**
Text: "Device flush counts (`/proc/diskstats`) confirm that every counted run uses the configuration that passed."
- diskstats counts flush requests, not FUA writes. With `fua=1` on the R640, SNC's steady-state overwrites, and possibly PG's or Restate's, show few or no flushes. The check gives false alarms and proves nothing.
- Fix: check that the binary hash, config file hash and command line are identical to the configuration that passed. Add a 10 s `blktrace` sample per counted configuration, showing F or FUA flags on the data device.
- The cloud test with `fua=0` (finding 1) does not run the same I/O path as the R640 with `fua=1`. State that gap and label it UNRESOLVED.

**4. MAJOR: tuning can produce a configuration that was never verified.**
- The 12-configuration screen runs "on the R640 inside the session", after the cloud durability test. Several knobs touch durability (`--aof-physical-sublog-count`, local or replicated loglet, partition count, `commit_delay`).
- Fix: screen first, then run the durability test on the winning configuration (falling back to the next best if it fails), then make the counted runs. Change the gating rule to "the first configuration in the order whose winning tuned configuration passes".

**5. MAJOR: the 100 µs probe loads each system unequally, and the plan's claim that the polling adds the same interval to each is false.**
- In Restate, every poll on an exclusive handler is a full journaled invocation with an fsync. It is also queued behind the credit on the same key. At the 10 ms B2 SLO that can be up to 100 invocations per probed transfer, which may saturate Restate.
- For Garnet the plan says "read after its commit-waited acknowledgement". That is one read with no grid wait, while SNC pays up to 100 µs of grid wait plus repeated reads. This favours Garnet and PG and penalises Restate. Neither direction is labelled.
- SNC's reads block until durable, so polls can pile up on one target.

Smallest fix:
- One outstanding poll per target. The next poll goes at the later of the next grid tick and the previous reply.
- Poll interval = SLO/20 (100 µs in B1, 500 µs in B2).
- Every system polls from the intended send on the same grid. For Garnet, observation = the later of the first visible poll and the acknowledgement.
- Probe reads are counted, reported and capped (for example at 1% of operations).
- For Restate, use a cheaper read that is still durable (shared handler or SQL `state` introspection; whether either is durable is UNRESOLVED). If none qualifies, label the gap "favours SNC, used for decisions".

**6. MAJOR: the probe pool is not specified.**
Text: "dedicated probe accounts that receive nothing else".
- If the pool is small, a probe account is a hot key. That causes RUNTXP 2PL and PG row-lock contention, while SNC only grows inbox entries. This favours SNC.
- A second probed transfer to the same account before the first is observed makes the observation ambiguous.
- Fix: each probe account has at most one outstanding probed transfer. The reader checks for balance equal to the prior balance plus the amount. The pool is large (at least probe rate × p99.9 settle × 10). Probe accounts are spread evenly across shards and partitions. Probe targets follow the same `--xfer-local` rule, so B2 probes are cross-shard.

**7. MAJOR: the cap on PostgreSQL is applied in B1 but not in B2.**
- B1: "Against PostgreSQL a PASS is recorded as NARROW at most", because of the SQL boundary.
- B2: "The outbox … no cap applies."
- The B2 claim is "infrastructure built for durable work between entities". A PG outbox is not that, and by B1's own reasoning it should be capped too.
- The B1 justification is also partly wrong: the 9-50x figures came from client-side logic, and PL/pgSQL removes most of that boundary.
- Fix: one rule for both benchmarks. Either cap a PASS against PG at NARROW in B1 and B2 alike (simplest), or use no cap anywhere and state in section 6 that a PG-gated result answers a narrower question.

**8. MAJOR: some debit-acknowledgement effects still reach the gated capacity.**
- The bounded backlog "includes unsettled transfers", but the plan never defines how they are counted for each system. The client frees a window slot at the debit acknowledgement, so the default count favours SNC.
- Fix:
  - SNC: count outbox entries summed over shards (or `emits_now`) at the end of the window.
  - Restate: count pending invocations through SQL introspection.
  - Outbox: count outbox rows.
  - Garnet and PG: zero.
  - The limit is the same absolute number for every system.
- Also, B1 correctness uses only "`emits_now` reads 0". Use B2's stronger condition: `emits_now` reads 0 and no account has outbox entries, sampled in two quiet rounds. A credit retried while an inbox is full re-emits, and a single sample can read 0 transiently.

**9. MAJOR (UNRESOLVED): the PG outbox worker is a free lever.**
- The worker's poll or NOTIFY interval, batch size, number of workers and `SKIP LOCKED` settle the outbox's latency directly, and none of these is pinned.
- Fix: put them inside the 12-configuration budget, with an example design fixed before any run.

**10. MINOR: two gap labels are wrong or missing.**
- B1, Garnet reads that may see uncommitted writes: labelled "no; stated". But read p99 gates capacity at both points, so it is used for decisions. The gap is conservative for SNC; relabel it "the baseline; yes (read p99)".
- B2, acknowledgement points: labelled "varies". Replace with "SNC and outbox (debit) ahead of Restate (handler end); reporting only".
- Add a row: the cost of a durable read differs by system (Restate's is highest). Label it according to finding 5.

**11. MINOR: Garnet FileStream may be over-durable.**
- If `WriteThrough` applies to every Tsavorite device, not only the AOF, Garnet pays for synchronous writes to the main log as well. This biases toward SNC. Whether the AOF device type can be set on its own is UNRESOLVED.
- Fix: size `--memory` so the 1M × 200 B accounts never spill to disk, and keep checkpoints out of the window. Label any remaining effect "favours SNC".

**12. MINOR: the "present" check for deposits is undefined.**
- Deposits are increments, so presence has to be checked against balances.
- Fix: per account, recovered balance ≥ start + acknowledged deposits before the mark, and ≤ that plus deposits in doubt.
- Record each mark's time before calling `dmsetup message`, and compare it with acknowledgement times on the same CLOCK_MONOTONIC host.

**13. MINOR (KISS):** 200 marks per system across 5 configurations means about 1,000 recoveries at 1M objects, plus a large log device.
- A missing flush shows at almost every mark, so 20 marks per configuration is enough once the controls of finding 2 are in place.
- Run the test at a fixed fraction of capacity, about 25%, so group commit is exercised.
- `replay-log` must be built from xfstests `src/log-writes`. Its availability on the bring-up VM is UNRESOLVED.

**14. MINOR:** the 2 ms B1 settlement SLO is fair if finding 5 is applied, since atomic systems then pay the same grid. Without that fix, atomic systems get up to 100 µs of headroom that SNC does not.

**Not broken:**
- The gating order Native, then FileStream, then PG is sound as a fixed order.
- Restate's request-response ingress gives the right acknowledgement point.
- Using only full settlement for decisions satisfies review item 3, subject to findings 5, 6 and 8.
