## 5. Event delivery / ordering / follow-ups  -- CLASSIFICATION: Implemented, unverified (as a general guarantee); Verified only for transfer-type idempotence tests
Key finding: there is NO first-class "event" concept. grep of include/ and src/ for "event" yields only epoll/eventfd and trace lines. The only asynchronous inter-object mechanism is the follow-up (OpCtx::emit, NodeLinks::Frame{source,target,op,fail_op,args[16]}, node_link.h:~38-45) stored as per-object state (outbox/inbox in the Account type, types/account.cpp:140-345). No publish/subscribe, no event log, no per-subscriber ordering, no event IDs.
Delivery semantics as implemented: AT-LEAST-ONCE via re-emission from durable object state, EXACTLY-ONCE EFFECT only because each op type is hand-written idempotent (account.cpp:257-285 credit applies once per (source, seq) and answers every copy). The engine does not enforce idempotence for other types (type-author contract; invariant 15, TRANSFERS.md:94-129). No transport acks (node_link.h:15-17); END/SYNC frames count items for backpressure (D.2), they are not delivery confirmations.
Re-emission is event-triggered, NOT timer-driven: resume_all runs on start_serving (shard.cpp:1858), node link bound (node_link.cpp:818-819 -> shard.cpp:2085-2092), map change (shard.cpp:3768-3775), unseal/activate (shard.h:226, shard.cpp:3812). CORE_CONTRACTS O-2 states this explicitly (lines ~666-690, "Today: not guaranteed"). Silent drop paths exist: emit_result returns false for statuses outside {NOT_FOUND,TYPE_MISMATCH,UNKNOWN_OP with fail_op} (shard.cpp:3525-3546) leaving unsettled state until next resume event (INFERRED, doc says same).
Ordering: per-TCP-link FIFO only; no ordering across links/shards/groups; re-emission after resume can reorder or duplicate (account protocol tolerates by design). Client ordering: per (client_id, owner shard) sequence; owner answers dup before refusing (shard.cpp:177-221 and 430-436; run_exec session check). Request sequencing assumes single in-order connection per shard; misrouted sequenced request gets E_NOT_OWNER (shard.cpp:~238-243). Gaps normal (failed ops not logged: record_session only on success, shard.cpp:~1212-1230 writes Status::OK).
Invariant 18 (duplicate before invite-a-resend refusal): verified at execute() E_MOVED bypass (shard.cpp:177-182), follow-up gate (190-221), exchange gate (430-436), and run_exec path; test_resend_refusals.cpp (in-process, 207 l, no kill: E_MIGRATING and E_MOVED, restart from dir). Also E_OVERLOADED+replayed = "applied, answer not ready" handled by client resend (client.cpp:281-300). Other E_OVERLOADED sites (pending_refuse shard.cpp:342-352 is only reached for non-sequenced since sequenced+non-owner returns E_NOT_OWNER first; owner_refuses shard.cpp:1585-1594, 1716-1722 are cross-shard EXEC_REQ at the owner) - I did not exhaustively prove every refusal site is after replay check: Unknown for the cross-shard owner_refuses path (lines ~1585-1594, 1716-1722: refusal returned before run(), where replay_if_seen would run) -> RECOMMEND targeted test.
Session horizon: wall-clock TTL (touched_s uses ::time, shard.cpp~1226; expire_sessions 1236-1253); an expired session means the dup applies again (FAILURE_MODEL W2/R11 KNOWN ISSUE, test_session_ttl demonstrates). Expiry only at checkpoint (CORE_CONTRACTS:306-311). client_id is caller-chosen, collisions out of contract.
Evidence: test_intake.cpp (D.1 intake, 1414 l, 5 kill sites), test_transfer.cpp (3), test_xnode*, test_baseline_retry.py (real net_bench --session --verify with SIGKILL/SIGSTOP/partition via proxies/flap/stall; exact balances), test_ready_order.py, test_replication.cpp test_retries_failover (30K resends).
Demonstrated: no double apply / no loss in listed scenarios, conservation after restarts and SIGKILLs; in-doubt answers kept visible.
Unverified: any ordering guarantee; "exactly-once" beyond session horizon; SETTLED observability (O-5); backoff (O-4); cross-group client dup (sec 4).
Next: decide whether an "event" abstraction is intended at all; if not, stop using the word; add timer-driven resume or prove all drops are paired with an event.

## Cross-cutting hazards found (verified in code)
H1. Without --witness the sync primary's degrade gate is null: degrade after timeout alone (shard.cpp:2252-2271; engine.cpp:859 only set when replica_degrade_gated).
H2. Fencing of a partitioned old primary is contact-driven (replication.cpp:667-669; shard.cpp:920): until contact it may serve default reads (INTERACTION_MATRIX.md:52, untested).
H3. Async standby can be promoted stale; no witness exclusion (snc_witness.cpp has no async check; shard.cpp:2759-2764).
H4. Obligation re-emission has no timer; only restart/link-up/map change/unseal (shard.cpp:1858,2085-2092,3768-3775,3812; node_link.cpp:818).
H5. Silent follow-up drop path in emit_result default (shard.cpp:3525-3546) and withdrawn-shard return.
H6. Sessions are per-shard objects not moved with slots; ClusterClient uses separate Client/seq per group (cluster_client.cpp:80-90); cross-group resend double-apply is unproven-not-excluded (CORE_CONTRACTS.md:313-322).
H7. Session expiry uses wall clock and runs only at checkpoint (shard.cpp expire_sessions; CORE_CONTRACTS:306-311) -> R11 duplicate after expiry.
H8. Unauthenticated admin/witness/replication/node-link/client ports (FAILURE_MODEL "Out of contract"; Hello in replication.h has only uuid/term).
H9. STATUS.md has contradictory bullets on migration staging (538 vs 561) and stale "no acks" row; CORE_CONTRACTS marked DRAFT yet cited as authority by FAILURE_MODEL.
H10. Fenced primary requires manual --rejoin; after any automatic failover the group runs without replica (FAILURE_MODEL P1; flapping has no hysteresis N7).
Unknown: whether any randomized/linearizability checker exists for HA; real-host behavior of D.1/D.2; whether owner_refuses (shard.cpp:1585-1594, 1716-1722) sits after the session replay check for sequenced cross-shard requests (client sends sequenced to owner directly so likely unreachable; not proven).
