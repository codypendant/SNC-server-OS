## 3. The recvfrom validity ratio 0.81-0.82 (reviewer hypothesis: window mismatch)
Verified facts:
- Ratio per run in characterization.json: 0.8097-0.8207 (15/15), min 0.8097, max 0.8207. Formula, capstate.py:454-458: ratio = sum(perf server sys_enter_recvfrom, intervals 1..60) / (req / fr), where req = FIRST "total: requests N" in the server log and fr = frames/recv from the same line (capstate.py:80-86).
- Server log line is printed once at shutdown (tools/snc_server.cpp:1511-1515) from per-shard CUMULATIVE counters since process start: requests = st.requests, recvs += conn.recv_calls, frames += conn.frames_in (:1493-1495; src/net/conn_set.cpp:105-106, 140). So both numerator inputs (req and fr) are whole-process-life values; the perf numerator is the 60 s window only. THE WINDOWS DO NOT MATCH. Hypothesis CONFIRMED in kind.
- recv_calls counts every ::recv call including EAGAIN (conn_set.cpp:105-111), not only data-bearing ones. frames_in counts frames. Cumulative frames/recv therefore includes the load phase and idle polls.
- Concrete reconciliation for A-capstate-k1-C1 (raw/A-capstate-k1-C1.{client,server}.log): the process lifetime includes a preceding net_bench load (5,000,000 creates in 6.23 s, a --seconds 0 priming run of 512 ops) and then the measured 60 s run (which "loads" 0 objects, 0.01 s). Server total requests 302,652,435 = window latency n 297,651,907 (this INCLUDES 38,845,422 overloaded refusals) + 5,000,000 creates + 528 (512 priming + 16 other). So the requests term is whole-life, and includes load.
- perf recvfrom sum, intervals 1..60 = 15,489,292; all 80 intervals = 15,844,125 (perf-server.csv).
- Arithmetic: expected recv calls (whole life) = 302,652,435/15.7 = 19.28M; perf window 15.49M => ratio 0.8165 (matches 0.8165 in characterization.json). By requests alone the window is 297.65/302.65 = 98.3% of life, so the request-window mismatch explains only ~1.7 points of the 18-19 point gap. The rest (~3.4M recv calls) must be recv calls outside the perf window or not tracked by it.
Inference (NOT directly verified): the remainder is consistent with the unmeasured load phase (5M creates in 6.2 s at low batching; ~1.4 frames/recv would account for all of it) plus post-window/idle/EAGAIN recvs; I could not verify this because perf was not recording during the load phase and no load-only server log exists. Also unverified: that sys_enter_recvfrom captures all recv() syscalls from the server CPU set (glibc recv -> recvfrom syscall, likely yes; admin/replication threads off the pinned CPUs would be missed but are not expected to matter), and that perf counting with -a -C is exact (perf's own "interrupt took too long" notices occurred in A2-a).
Consequences (verified): (a) the "instrument defect" flag is largely a DENOMINATOR DEFINITION error in the preregistered check (whole-life server counters vs window counter), not evidence of an observer effect; its constancy across runs (all runs have the same 5M load) is what a fixed load-phase offset predicts; (b) the same cumulative frames/recv is what the state classifier (boundary 15.0, capstate.py:28,78) and the earlier A2-a "13.2-13.9 vs 15.6-15.8" separation use, so the classification is consistent run-to-run across all experiments (same blend), but the absolute frames/recv in the 60 s window is higher (inferred ~19) and the 15.0 boundary is a property of the blended metric; (c) PREREG section 0 item 3 observer-effect concern stands as unresolved but this check provides no evidence for it.
Cannot verify: window-only frames/recv from the server (no windowed snapshots of server counters exist), and whether the sar.sa-derived columns are sound (350 MB sar.sa not committed; hashes in SHA256SUMS only).

## 4. Robust vs confounded numbers
Robust (reproduced across sessions, small CV):
- Profile A open-loop p99 at 654,569 ops/s: ~0.93-1.0 ms in CP-1A (5 fixed + 3 sweep reps, CV 1.9%) and A2-a (5 sessions, 12 runs each, anchors 0.93-1.03 ms, between-session CV 1.4%).

Confounded / state-dependent:
- Closed-loop capacity at saturation: bimodal ~+8% (4.26-4.36 M vs 4.0 M) tied to server batching state (15.4-15.9 vs 13.2-13.9 frames/recv). State not seen to vary within the capacity-state run; not separable from instrumentation (perf/sar). Anything quoted as "capacity" in a Profile A comparison is state-sensitive within ~8%.
- Open-loop p99 between sessions: duration validation 1.47 ms (60 s) vs CP-1A/A2-a 0.93-0.98 ms at the same rate (~1.58x). Time since fstrim (6 h CP-1A; ~11 h duration; 0 after A2-a explicit trim), 0.2-1.9 TB written, and run order/time are all confounded. A2-a post-trim anchors (983,040) are close to CP-1A, consistent with (not proving) a storage-state effect. Hypothesis only.
- Duration validation: window length vs run order confounded; 240 s cell at one histogram bucket from its bound.
- p99.9: quantized at ~2.7-5% bucket steps near 10 ms; REFINE #1 pass = 0.39% margin. At the 654,569 objective rate p99.9 is 8.4-8.9 ms (CP-1A fixed) to 10.2-11.0 ms (duration 60 s reps): level not stable between sessions.
- Observer effect: instrumented capacity runs (3 perf stat, 1 s sar, snapshots on CPUs 34/70) vs uninstrumented A2-a. Unresolved.
Not robust / do not quote: INVALID-pilot-r640-20261106-stopped (README says no number usable); manifest-d CP-1A/diagnosis results are "historical"; devvm numbers.

## 8. Validated conclusions
1. S6 as preregistered FAILED on p99.9 only (rules 1-3,5-7 and capacity guard pass); REFINE #1 (W=1) PASSED the identical criteria with a thin margin; W=1 is the approved Profile-A checkpoint config. One REFINE rescue remains unused. (s6-r640, s6-refine1.)
2. CP-1A is complete and valid; SNC Profile A stable peak 1.09 M (refusal-limited), objective 654,569 ops/s at p99 ~0.93-1.0 ms; closed-loop capacity ~4.0 M; Profile C 5.78 M / 6.03 M. Mechanism for A's refusal knee is the checkpoint/backpressure design gap, accepted.
3. Open-loop p99 at the objective rate is reproducible in a trimmed-and-settled state (A2-a: between-session CV 1.4%, within <=4.2%, sentinels <=1.053); the A2-a STOP concerns closed-loop throughput modality, not the p99 objective.
4. Closed-loop capacity at saturation is state-dependent (~8% bimodal in A2-a; all-high with instrumentation); cause unknown; not attributable to host-state telemetry that exists.
5. The 0.81-0.82 recvfrom "instrument defect" is substantially explained by comparing a window-only tracepoint count to whole-process-life server counters (load phase 5M creates + priming + 298M window requests incl. refusals); the request-window part alone is 1.7 points; remainder inferred (load-phase recv calls). It is not evidence of observer effect.
6. No comparative (competitor) campaign data exist; CRITERIA.md not committed; no GO/NARROW/STOP evidence yet. Profile B untested on R640.
7. Pre-campaign dev-VM comparisons are numerically faithful to their csv but are not like-for-like and, per the project's own rule, not campaign evidence.
